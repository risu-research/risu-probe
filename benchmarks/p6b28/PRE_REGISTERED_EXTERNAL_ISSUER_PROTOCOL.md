# RISU Probe P6-B28 | Preregistered cross-publisher issuer-to-resource verification

**Frozen before live CI results.** Base: independently verified P6-B27 PostgreSQL and SeaweedFS comparison. B28 introduces a third independently published original backend as an **issuer**, OpenBao v2.7.2 (openbao/openbao), which creates short-lived native PostgreSQL credentials using its database secrets engine. The actual resource remains an unmodified PostgreSQL server. The issuer and resource service are from independently governed software projects; both are hosted by RISU in isolated GitHub CI, so this does not amount to a separate human or external operator.

## Upstream sources and immutable identity

- Official issuer release: https://github.com/openbao/openbao/releases/tag/v2.7.2
- Original Linux amd64 archive: `openbao_2.7.2_linux_amd64.tar.gz`
- Official release checksums file (SHA-256 of **checksums.txt**): `d839d376448eceef3ccb5cdd44c4a0749a92a6e4aa2fdaf47255cfa949dfb77e`; resolve archive checksum from this verified list, fail closed on mismatch.
- Official PostgreSQL plugin documentation: https://openbao.org/docs/secrets/databases/postgresql/
- Native OpenBao database secrets, dynamic roles/leases/revocation: https://openbao.org/docs/secrets/databases/
- PostgreSQL native RLS: https://www.postgresql.org/docs/current/ddl-rowsecurity.html

## Frozen narrow intent

Authorized: only existing `approved/report` row, from `WAITING` and `ORIGINAL APPROVED` to `APPROVED` and `APPROVED CONTENT`. Neighbor `approved/report-extra` and `foreign/other` must remain unchanged. Only the resource-owning PostgreSQL user sets RLS, forces row security, and grants limited UPDATE(state,body) privileges to a NOLOGIN template role. OpenBao's separate DB management login is allowed to create ephemeral roles and grant the template membership, but is not an RLS bypass superuser. The requesting agent receives neither the owner account nor the OpenBao operator token.

## Frozen verification cases

1. Distinct original OpenBao and PostgreSQL server processes. Keep issuer/operator and DB owner outside the agent PID/UID and do not forward root/operator env to agent. The actor runs as Linux UID 65534. The attacker probes direct native PostgreSQL SQL, without any RISU gateway.
2. An OpenBao native read-only path policy allows **only** issuing credentials for `database/creds/b28-write`; its token has `num_uses=1`, cannot issue a second credential and cannot obtain operator or other-role credentials. The dynamic SQL username and password must be generated by **OpenBao's original PostgreSQL database plugin** on actual service response, not minted by RISU.
3. Using the single dynamic PostgreSQL credential, the actor tries (before the authorized transition): cross-object UPDATE; same-prefix neighboring row UPDATE; changed output bytes; unauthorized direction; altered immutable owner_epoch; INSERT; DELETE; ALTER RLS; SET ROLE postgres; cross-row SELECT; and disabling row_security. Each must fail or affect zero rows. Compare exact three original rows before and after the denied probes.
4. Native valid UPDATE must modify exactly one row, then replay must modify zero; three original-row SHA hashes / byte content must agree with the owner-declared target. A new database connection after OpenBao's native lease revocation must fail to authenticate using the same leased credentials.
5. A **separate independently authored audit script** does not import the issuer harness or actor. It separately fetches original PostgreSQL rows and system catalogs, checks FORCE RLS and native policy, owner vs issuer role membership, absence/revocation of the issued ephemeral role, and all case outcomes. It must refuse altered original evidence.
6. Archive original nonsecret evidence: upstream checksum proof, PG version, OpenBao version, actor UID, lease ID (no secret), dynamic DB user name (no password), exact before/after state, denial categories, independently checked audit. NEVER persist OpenBao root token, actor OpenBao token, PostgreSQL passwords or `/proc` content.
7. The original database server must enforce restrictions even if the actor bypasses all RISU code; OpenBao must revoke the leased database credential while the actor retains its original password in memory. The actor's subsequent **direct** database connection must fail.

## Predeclared failure labels

- `ISSUER_CONFIGURATION_UNQUALIFIED`: original OpenBao binary or database backend unavailable, checksum wrong, native role provisioning failed.
- `EXTERNAL_ISSUER_SCOPE_BYPASS`: actor could access another OpenBao credentials path, reuse one-use capability, or obtain operator access.
- `EXTERNAL_RESOURCE_AUTHORITY_BYPASS`: original PostgreSQL allowed wrong resource/bytes/direction or privilege escalation, or changed another row.
- `LEASE_REVOCATION_NOT_ENFORCED`: original OpenBao reports revocation but original PostgreSQL still authenticates same credential in a fresh connection.
- `B28_CROSS_PUBLISHER_ORIGINAL_EFFECT_PASS`: valid update exactly once and all original issuer/resource negative controls and independent audit pass.

## Strict interpretation

OpenBao/Pg original native mechanisms are known tools. The experiment tests **composition across original independently developed systems**. No unrelated independently controlling human approves a live action in this fixture; the CI owner and root admin remain trusted. A valid token may issue one database credential (one token use), while that credential could persist until lease revocation; it is not intrinsically a cryptographically one-use database capability. The original row precondition enforces one-way transition. A malicious service/admin remains out of scope.

**No policy tuning against holdout outputs.** If a provisioning dependency fails, document and repair only infrastructure/configuration; do not silently broaden the original authorized row scope. B27 remains a frozen prior positive/control set.
